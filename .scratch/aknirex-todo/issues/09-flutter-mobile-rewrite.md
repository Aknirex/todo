# 09 — Flutter 移动端重构

**Status:** ready-for-agent

## Problem Statement

aknirex-todo 的设计文档和原型已经基本满足产品预期，但现有 UniApp 实现落到真实移动设备后，交互与视觉还原度不足。当前实现存在状态栏遮挡、触控目标偏小、输入框尺寸与键盘行为不稳定、新建 Todo 不能正确聚焦详情、系统返回时编辑内容丢失等移动端体验问题。

现有技术方案还同时承载微信小程序、PC 小程序、Android、AI、Agent API、同步和云端扩展，导致实现受到不再需要的跨端约束。产品首发目标已收敛为简单、可靠的 Android+iOS 移动 App，需要在不改变已确认领域语义的前提下直接替换根工程并重建客户端体验。

## Solution

将根工程重构为 Flutter Android+iOS 移动 App，使用真正的移动端输入、键盘、系统返回、手势、状态栏和安全区能力。应用保持本地优先、离线可用，不引入账号和云端同步。

首版围绕 Todo 的本地闭环展开：用户打开 App，快速创建 Todo，查看和编辑 Todo，标记完成，使用搜索、筛选、排序定位内容，并通过持久化的 Undo/Redo 修正误操作。现有 Priority、DueDate、Tag 和 Detail 字段继续保留，但不增加录入主路径的负担。

首版使用 Flutter、自有 Design System、Drift/SQLite 和 Riverpod。应用提供简体中文与 English，保留浅色/深色主题，并提供 JSON 备份导出和导入能力。

## User Stories

1. 作为 Android 用户，我想在真实移动 App 中打开 aknirex-todo，以便获得稳定的状态栏、安全区和键盘体验。
2. 作为 iOS 用户，我想在真实移动 App 中使用 aknirex-todo，以便获得符合 iOS 返回、输入和触控习惯的体验。
3. 作为 Todo 用户，我想在首页看到未完成 Todo 和已完成 Todo 的清晰分段，以便快速判断下一步要做什么。
4. 作为 Todo 用户，我想点击首页右下角的“+”打开新建编辑页，以便快速开始记录 Todo。
5. 作为 Todo 用户，我想进入新建编辑页后自动聚焦详情输入框，以便无需额外点击就能开始输入。
6. 作为 Todo 用户，我想在新建编辑页中填写标题、详情、Priority、DueDate 和 Tag，以便完整描述一个 Todo。
7. 作为 Todo 用户，我想点击明确的“创建”按钮提交新 Todo，以便知道什么时候真正产生了记录。
8. 作为 Todo 用户，我想即使标题和详情都为空也能点击“创建”，以便先记录一个待补充的空白 Todo。
9. 作为 Todo 用户，我想点击页面内的返回按钮放弃尚未创建的新 Todo，以便误触新建时不会产生记录。
10. 作为 Todo 用户，我想在新建页第一次按系统返回时先收起键盘，以便继续编辑而不意外离开页面。
11. 作为 Todo 用户，我想在键盘已经收起后再次按系统返回时回到首页且不创建 Todo，以便系统返回与页面返回都不会误提交。
12. 作为 Todo 用户，我想在首页看到空白 Todo 仍然占据一行，以便能够再次找到并补充它。
13. 作为 Todo 用户，我想在 Todo 有内容时优先看到标题，没有标题时看到详情内容，以便快速识别 Todo。
14. 作为 Todo 用户，我想点击 Todo 行进入详情编辑页，以便补充或修改 Todo 内容。
15. 作为 Todo 用户，我想在详情页编辑 Todo 的多个字段后一次性保存，以便一次编辑只代表一个完整的用户意图。
16. 作为 Todo 用户，我想通过页面返回、Android 系统返回或返回手势离开详情页时自动保存变更，以便编辑内容不会丢失。
17. 作为 Todo 用户，我想在没有修改内容时离开详情页不产生 Undo 记录，以便历史不会被无意义的操作占满。
18. 作为 Todo 用户，我想点击 Todo 的完成控件切换完成状态，以便快速追踪执行进度。
19. 作为 Todo 用户，我想空白 Todo 也能被标记完成，以便所有 Todo 遵循一致的生命周期语义。
20. 作为 Todo 用户，我想删除单个 Todo 时不被确认弹窗打断，以便高频清理操作足够顺手。
21. 作为 Todo 用户，我想删除后的 Todo 能通过 Undo 恢复，以便误删时不会丢失内容。
22. 作为 Todo 用户，我想看到当前可用的 Undo 和 Redo 按钮状态，以便知道是否还能恢复或重做操作。
23. 作为 Todo 用户，我想在首页和详情编辑页都能执行 Undo/Redo，以便不必返回特定页面才能修正操作。
24. 作为 Todo 用户，我想 Undo 和 Redo 在 App 重启后仍然可用，以便短暂退出 App 不会破坏我的操作历史。
25. 作为 Todo 用户，我想一次详情编辑的多个字段只占用一个 Undo 步骤，以便按用户意图而不是按键盘输入回退。
26. 作为 Todo 用户，我想 Undo 和 Redo 各自最多保留 50 步，以便历史有明确上限且不会无限增长。
27. 作为 Todo 用户，我想执行新的创建、编辑、完成或删除操作后 Redo 历史被清空，以便历史符合标准编辑器语义。
28. 作为 Todo 用户，我想执行 Undo 后不会产生新的 Undo 记录，以便连续回退可以按时间顺序到达更早的操作。
29. 作为 Todo 用户，我想所有 Todo 自动归入唯一的默认 List，以便首版不需要先管理多个 List 才能记录内容。
30. 作为 Todo 用户，我想默认 List 在本地数据库初始化时始终存在，以便空数据库首次启动也能立即创建 Todo。
31. 作为 Todo 用户，我想 Priority 有 high、medium、low 三档且默认为 medium，以便表达我的主观重要性。
32. 作为 Todo 用户，我想 Priority 只影响展示、排序和筛选，不自动改变 DueDate 或触发通知，以便系统不会替我推断紧急程度。
33. 作为 Todo 用户，我想 DueDate 只表示设备本地时区中的某个日历日期，以便今天、本周和逾期筛选不会受到 UTC 转换影响。
34. 作为 Todo 用户，我想 Tag 是自由文本且同一 Todo 内自动去重，以便用自己的分类方式组织 Todo。
35. 作为 Todo 用户，我想 Tag 输入会去除首尾空白并忽略空标签，以便搜索和筛选结果保持一致。
36. 作为 Todo 用户，我想默认首页按未完成优先、最新创建优先显示 Todo，以便刚记录的内容立即可见。
37. 作为 Todo 用户，我想已完成 Todo 排在未完成 Todo 之后并按最新更新优先显示，以便完成记录仍可查找但不阻塞当前工作。
38. 作为 Todo 用户，我想使用搜索查找 title、detail 或 Tag 中包含关键词的 Todo，以便不必手动浏览大量记录。
39. 作为 Todo 用户，我想搜索结果优先展示标题命中的 Todo，并高亮匹配内容，以便快速判断结果是否相关。
40. 作为 Todo 用户，我想组合关键词、Priority、Tag、完成状态和 DueDate 筛选，以便缩小结果范围。
41. 作为 Todo 用户，我想不同筛选维度按 AND 组合、同一维度多个值按 OR 组合，以便查询结果符合可预测的逻辑。
42. 作为 Todo 用户，我想搜索和筛选都在本地完成，以便离线时仍能定位自己的数据。
43. 作为 Todo 用户，我想在设置中切换简体中文和 English，以便使用熟悉的用户文案。
44. 作为 Todo 用户，我想 App 默认跟随系统浅色/深色主题，并可手动覆盖，以便在不同环境中保持舒适阅读。
45. 作为 Todo 用户，我想主题和语言选择在重启后保留，以便不必重复设置。
46. 作为 Todo 用户，我想在没有网络时正常创建、编辑、完成、删除、搜索和恢复 Todo，以便本地效率工具不依赖服务可用性。
47. 作为 Todo 用户，我想导出包含 Todo、List、主题和语言设置的 JSON 备份，以便换机或卸载前保护数据。
48. 作为 Todo 用户，我想将 JSON 备份合并导入当前 App，以便恢复数据而不必先清空已有 Todo。
49. 作为 Todo 用户，我想导入时看到同 ID 冲突报告而不是被静默覆盖，以便我能决定如何处理不同版本的数据。
50. 作为 Todo 用户，我想导入过程使用事务并在失败时完全回滚，以便不会得到半份备份数据。
51. 作为 Todo 用户，我想导入备份后从空 Undo/Redo 历史开始，以便旧设备的操作历史不会在新设备上产生误导。
52. 作为产品维护者，我想以 Flutter 统一 Android+iOS 客户端，以便不再为微信小程序运行时限制牺牲移动端交互质量。
53. 作为产品维护者，我想保留已确认的 Todo、List、Undo、Redo、DueDate、Priority 和 Tag 领域语言，以便技术迁移不改变产品含义。
54. 作为开发者，我想用自有 Design System 管理颜色、间距、圆角、字号和触控尺寸，以便视觉还原和跨页面一致性由统一令牌控制。
55. 作为开发者，我想所有关键交互控件达到至少 48dp 触控目标，以便现代手机上不需要精准点击。
56. 作为开发者，我想通过单一的应用层 Todo 工作区门面驱动页面行为，以便领域、持久化和 UI 之间有清晰且可测试的边界。
57. 作为开发者，我想用纯 Dart 领域测试验证 Todo 和 Undo/Redo 规则，以便核心行为不依赖 Flutter 页面生命周期。
58. 作为开发者，我想用 Drift/SQLite 事务验证本地数据与历史的一致性，以便 App 重启和导入失败时不会损坏用户数据。
59. 作为开发者，我想用 Widget、真机集成和 Golden 测试验证移动端行为，以便重构真正解决原型到真机之间的差异。

## Implementation Decisions

- 将客户端根工程替换为 Flutter Android+iOS 工程，不把微信小程序、PC 小程序或 H5 继续作为运行目标。
- 不迁移现有 UniApp 本地数据库数据。重构后的 App 使用新的存储模型，不为旧版本增加兼容层。
- 采用 Flutter、Dart、Drift/SQLite 和 Riverpod。Riverpod 负责依赖注入、应用状态和异步协调，Drift 负责类型安全的关系数据访问、迁移与事务。
- 按领域、应用服务、持久化和展示职责分层。页面不直接操作 Drift 或数据库表，只通过应用层 Todo 工作区门面执行命令和读取查询结果。
- Todo 工作区门面是最高层行为 seam，统一承载创建、编辑、完成、删除、搜索、筛选、Undo、Redo、备份和导入等用户可观察行为。
- 保留 `Todo`、`List`、`Undo`、`Redo`、`DueDate`、`Priority` 和 `Tag` 的领域语言，避免使用 `Task`、清单、列表、截止时间、紧急程度等替代概念。
- Todo 保留 title、detail、priority、dueDate、tags、completed、createdAt 和 updatedAt 等字段。title 和 detail 都允许为空，完全空白的 Todo 仍是正式 Todo。
- Todo 创建时 Priority 默认为 medium，Tag 为空集合，DueDate 为空，completed 默认为 false。
- 空白 Todo 在首页保持可见并占据一行；有内容时优先显示 title，没有 title 时显示 detail 内容。
- Todo 可在任意内容状态下切换完成；完成、编辑、删除和恢复不因空白状态产生特殊生命周期。
- 首版保留一个真实的默认 List，但不提供 List 新建、重命名、删除或切换 UI。List 领域边界为未来多 List 扩展保留。
- 单个 Todo 删除直接执行，不弹确认；删除结果从当前可见 Todo 集合移除，并保留足够快照供 Undo/Redo 恢复。未来 List 级联删除必须二次确认，并作为一个原子历史命令。
- 新建流程从首页右下角“+”进入编辑页并自动聚焦 detail。只有点击“创建”按钮才提交新 Todo；页面内返回按钮放弃创建；系统返回第一次只收起键盘，键盘已收起后返回首页且不提交。
- 详情编辑页不增加显式保存按钮。页面返回、系统返回和返回手势离开时保存一次；未发生字段变化时不产生历史记录。
- 一次详情编辑会话的多个字段变化合并成一个 UpdateTodo 业务命令，不按每次输入或每个字段写入 Undo/Redo。
- Undo 和 Redo 各自最多保留 50 步并跨 App 重启持久化。Undo 将最近业务命令移入 Redo 并应用反向变更；Redo 将命令移回 Undo 并重新应用；Undo/Redo 本身不创建新的业务命令。
- 任何新的创建、编辑、完成或删除业务命令都会清空 Redo；各栈超过 50 步时丢弃最早记录。
- 首页和详情编辑页都显示 Undo、Redo 控件，并在对应栈为空时置灰；不使用摇晃撤销、系统快捷键或隐藏手势。
- DueDate 使用本地日历日期值，不表示具体时刻；今天、本周、本月、逾期和无日期筛选按设备本地日历计算。
- Priority 是 high、medium、low 三档的用户主观重要性，只影响展示、排序和筛选，不触发通知或自动计算。
- Tag 是 Todo 持有的自由文本集合；保存前去除首尾空白、丢弃空标签、同一 Todo 内去重，不建立独立 Tag 实体。
- 首页默认按未完成优先、createdAt 最新优先展示；已完成 Todo 位于后段并按 updatedAt 最新优先展示。用户可切换 Priority、DueDate、alpha 等排序方式。
- 搜索覆盖 title、detail 和 tags，使用本地包含匹配；关键词与筛选可组合。不同筛选维度之间使用 AND，同一维度多个值使用 OR；标题命中优先并高亮匹配内容。
- 搜索和筛选使用本地查询，输入搜索支持约 300ms 防抖；单一默认 List 下不暴露 List 筛选 UI，但查询模型为未来多 List 保留 List 条件。
- App 完全本地优先和离线可用，不引入账号、网络依赖、云端同步、Agent API 或服务器存储。
- JSON 备份包含 Todo、List、主题和语言设置，不包含 Undo/Redo 历史。导入默认采用合并策略，保留备份 ID；同 ID 内容冲突时报告冲突，不静默覆盖。
- JSON 导入在单一数据库事务中完成；校验失败、冲突处理失败或写入失败时整体回滚，不产生半完成导入。
- 提供简体中文和 English。本地化资源与领域代码分离，不在页面中散落硬编码用户文案。
- 默认主题跟随系统浅色/深色模式，用户可手动覆盖；覆盖值持久化到本地设置。
- 建立项目自有 Design System，统一颜色、字号、间距、圆角、控件状态、键盘安全区和触控目标；底层使用 Flutter primitives，Material 仅作为基础能力，不直接暴露默认页面样式。
- 交互实现必须处理 Android/iOS 状态栏、安全区、键盘弹出与收起、系统返回、返回手势、焦点转移和页面恢复。
- 直接替换根工程意味着现有 UniApp 实现、UniApp 构建配置和旧移动端运行时不再是首版实现边界；现有文档和代码只能作为产品、领域和行为参考，不能作为新架构的兼容约束。
- 本地测试的最高行为 seam 是 Todo 工作区门面。页面通过该门面执行用户行为，Drift 适配器通过同一应用边界提供真实持久化；不让 Widget 直接依赖数据库实现。

## Testing Decisions

- 测试只验证外部行为、领域规则和用户可观察结果，不验证 Riverpod provider 的具体数量、Widget 私有状态、SQL 字符串或内部类层级。
- 以 Todo 工作区门面作为最高测试 seam，使用内存或测试数据库验证从命令到查询结果、Undo/Redo 和导入导出的完整行为。
- 纯 Dart 领域测试覆盖空白 Todo、默认字段、Priority、DueDate、Tag 规范化、List 归属、完成切换、删除、编辑命令合并和 Undo/Redo 双栈规则。
- 应用层测试覆盖创建、编辑、完成、删除、搜索、筛选、排序、跨重启恢复历史、创建新命令清空 Redo、Undo/Redo 各 50 步上限以及 List 级联操作的原子语义。
- Drift 集成测试覆盖数据库初始化、默认 List、Todo 持久化、Undo/Redo 持久化、事务回滚、JSON 合并导入和同 ID 冲突报告。
- Widget 测试覆盖首页分段、空白 Todo 空行、Todo 行点击、完成控件、Undo/Redo 按钮状态、搜索筛选界面、主题切换和语言切换。
- Widget 测试覆盖新建页聚焦 detail、创建按钮提交空白 Todo、页面返回放弃、系统返回第一次收键盘和第二次离开不提交。
- Widget 测试覆盖详情页编辑后页面返回、系统返回和返回手势触发一次保存，以及无变更离开不生成 Undo。
- Flutter integration 测试至少覆盖一台主流 Android 真机和 iOS 模拟器或真机上的启动、状态栏安全区、键盘、焦点、系统返回、手势返回、滚动、搜索和核心 CRUD 流程。
- Golden 测试覆盖首页、Todo 行、空状态、新建编辑页、详情编辑页、搜索筛选状态以及浅色/深色主题的关键视觉状态。
- 真机验收必须确认所有关键可交互元素触控目标至少 48dp，文本不被裁切，键盘不遮挡当前输入，状态栏不覆盖内容，中文与 English 混排正常。
- 现有 Vitest 的 Todo store、repository、Undo、List、UUID 和平台测试是行为覆盖的参考；新实现应迁移其有效外部行为，而不是机械保留 TypeScript 测试文件或 UniApp 测试方式。

## Out of Scope

- 微信手机小程序、微信 PC 小程序、H5 和其他小程序平台。
- UniApp 运行时兼容、旧 UniApp 本地数据库自动迁移和旧客户端数据自动恢复。
- AI 拆解、Todo 总结、BYOK、LLM Provider、Agent 对话和第三方 Agent API。
- 账号、登录、云端数据、跨设备同步、加密中继、协作和多用户权限。
- 首版多 List UI，包括新建、切换、重命名、删除和 List 管理页面。
- 本地通知、提醒时间、重复 Todo、日历视图、甘特图和后台调度。
- 自动 Priority 推断、系统级紧急程度计算和独立 Tag 实体。
